### Implementation risks relevant to current DSH

The following are **verified source observations**, followed by **design inferences**. They are not a reproduced exploit assessment.

| Verified observation | Implication for a new plugin |
|---|---|
| The reference overwrites `WorkspaceRegistry.archiveSession` and `unarchiveSession`, directly reading and writing registry state. Its HTTP archive route only checks the agent registry for `status !== 'idle'`. | Do not copy these patches into the current host. Native archive admission now includes more activity families and preserves invariants this patch bypasses. |
| Its archive state is the host's `archivedSessionIds`, not a separately owned trash collection. | Calling every archived session “deleted” conflates the host's archive feature with plugin trash. Native archived sessions could unexpectedly appear in a bin or become purge targets. |
| `permanentlyDeleteSession` calls `rm(dirname(logPath), { recursive: true, force: true })`, then cleans cache/live/workspace state through several separate steps. | This removes the entire session directory, including retained generations and any colocated artifacts. The cleanup is not one transaction and can leave partial state if a later step fails. |
| Path resolution first probes old/internal persistence methods, then scans `HOME/.dsh/sessions`; it does not use DSH's configured data-root helper in that fallback. | Avoid guessed roots. Custom `DSH_HOME`, configurable JSONL roots, alternate providers, or future layouts require an explicit supported adapter. |
| Purge routes accept any non-empty string IDs and do not require membership in the archive set. The workspace-purge route also accepts caller-supplied IDs. | A new host endpoint should validate identifiers and each target's membership, capabilities, and current state. UI confirmation alone does not constrain what the backend will delete. |
| The recursive removal path is derived from persistence lookup or a `join(root, project, sessionId)` fallback without an explicit realpath containment assertion in the plugin. | Treat filesystem authorization and containment as required implementation work. Do not infer that a string session ID authorizes any path it happens to resolve to. |
| One delete wrapper suppresses original-delete and physical-delete failures, while cache removal is fail-soft; batch routes collect per-session errors but `emptyArchivedSessions` returns counts without its collected error details when any deletion succeeds. | Report actual per-target outcomes and retain failed items visibly. A “success” counter must correspond to verified completion. |
| The reference snapshots only active-agent status before filesystem work; it does not acquire the current persistence writer lease. | An idle loaded session can still own a write handle, and another process can be writing. Current safety needs persistence ownership coordination, not an agent-status check alone. |
| The host shim deliberately avoids a default export to preserve named `inject`; it content-hashes only the implementation entry on dynamic import. It also tags service patches and attaches cleanup through `ctx.effect`. | Lifecycle cleanup and reinstall behavior are material requirements. The shim is a workaround tied to its build shape; copying it is not proof that transitive imports or every host version reload safely. |
| The mutation-route guard checks a fixed `x-dsh-plugin` header. The reference describes this as a minimal CSRF defense. | This is a custom-header mechanism, not a secret or a complete statement of current DSH authentication. Validate integration with the installed host's transport and origin policy before exposing new mutation routes. |

All reference implementation observations in this table come from the [pinned host source](https://github.com/Seetraum/harness-session-delete/blob/c9f08e801cf46a917a49d785dc32e9e769e6d2a9/packages/session-trash-host/lib/index.js), [host shim](https://github.com/Seetraum/harness-session-delete/blob/c9f08e801cf46a917a49d785dc32e9e769e6d2a9/index.js), and [security policy](https://github.com/Seetraum/harness-session-delete/blob/c9f08e801cf46a917a49d785dc32e9e769e6d2a9/SECURITY.md).

### Current-host cross-checks

**Verified:** native `archiveSession(sessionId, options)` in `0.2.0-rc.2` checks whether the session exists, asks the `workspace/session-activity` waterfall, rejects activity unless `stopActivity: true`, clears the pin in the same durable state write, and can dispatch `workspace/session-stop` after archival. Shipped activity providers cover the running agent turn, owned jobs, running descendants, and active reminders. Native `unarchiveSession` already exists and removes only the archive marker. Replacing these methods with the reference's archive implementation would bypass current admission and pin handling. [Installed workspace implementation](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-workspace/lib/index.js#L507); [installed workspace contract](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-workspace/README.md#L99).

**Verified:** current persistence offers create/open/stat/list/flush and handle-based reading/writing. `open(id, 'read')` observes without ownership; omitting or confusing access is unsafe. Closing a write handle drains pending durability and releases ownership. The JSONL backend explicitly says “Nothing deletes session files” and “the seam has no deletion API”; it uses kernel-backed writer exclusion across instances/processes. Removing the POSIX lock file forfeits that exclusion. Permanent deletion therefore needs its own carefully scoped storage integration; it cannot simply call a public generic delete API that does not exist. [Installed persistence contract](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-session-persistence/README.md#L34); [JSONL limitations](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-session-persistence-jsonl/README.md#L163).

**Verified:** the JSONL root is deployment-controlled and required, with no backend default; logs may be compressed and retain historical generations. The shared home helper resolves explicit configuration, then `DSH_HOME`, then `~/.dsh`. The reference's filesystem fallback is narrower than these current contracts. [JSONL configuration](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-session-persistence-jsonl/README.md#L28); [home-path helper](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-home-paths/README.md#L12).

## Verified DSH package and browser contracts

### Bundle versus profile

An installable plugin is an npm **bundle** declaring `dsh.bundle.patch`; a runnable composition is a **profile** declaring `dsh.profile.bundles`. The plugin should ship a patch YAML array that mounts a package-named loader row. A package without `dsh.bundle` can install as a library dependency, but no bundle layer is activated. `patch` can be one relative file path or an ordered list of paths. [Official publication tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md); [installed manifest reference](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-package-manifest/README.md#L46).

`dsh plugin --profile <name> ...` forwards package-manager arguments to pnpm in that profile and maintains its installed bundle list. Patch layers compose in bundle order, followed by the profile patch, the home patch, and CLI overlays. Later row configuration replaces the complete `config` value rather than deeply merging it. A new package should insert its own stable row and avoid overriding core rows unnecessarily. [Official publication tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md).

### Browser artifact and native UI requirements

The host serves the **built** client export, not TypeScript sources. Dynamic browser bundles register lazy CommonJS factories through `window.__ModuleLoader__.load({ id, factory })`; arbitrary ESM browser output is not that protocol. React, Cordis, and static UI modules are supplied by the platform module table. The official tsdown preset supplies the wrapper and CSS lifecycle tagging, but that preset depends on DSH monorepo paths and internal helpers, so a standalone plugin cannot assume it is an importable npm build SDK. A standalone build must reproduce the supported artifact boundary and prove its emitted requests resolve. [Installed module-system reference](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/node_modules/@deepseek-ai/dsh-client-modules/README.md#L32); [official build preset](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/tsdown.client.ts).

For a polished native UI, official authoring guidance favors slots, framework-derived props/hooks, host localization, CSS Modules, `clsx`, existing UI primitives, and `--dsw-alias-*` semantic tokens. Menus use `Menu`/`MenuSurface`; theme branches belong to the theme owner; preserve focus visibility and reduced motion. This is a better basis than DOM title matching and a second global palette. These are upstream authoring conventions, not a new mandatory checklist invented for this project. [Official client rules](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/AGENTS.md); [official styling reference](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/web-styling.md).

## Proposed implementation and project conventions

These are **recommendations**, not verified product features or extra registry requirements.

1. **Separate Archive from Trash.** Preserve native archive semantics. Own a versioned tombstone/trash record that marks intentional removal, deletion time, and restoration metadata. If trash uses native archival for hiding, record whether the item was already archived and restore only the transition the plugin owns. Existing host archives should not silently become purge candidates.
2. **Deliver a session manager before a generic permanent-delete promise.** A native panel with search/filter/sort, explicit stable-ID selection, project grouping, preview, and per-item outcomes provides value. Use native session/workspace mutations where supported; enable irreversible deletion only behind an adapter that can prove ownership and containment for the supported backend.
3. **Fail closed on unsupported persistence.** Current generic persistence has no deletion capability. A JSONL adapter can be deliberately supported and documented; another provider should receive a clear unsupported-capability result while archive/restore remain useful.
4. **Use current activity admission.** Respect jobs, descendants, reminders, and writer ownership as well as the agent turn. A future “Stop and move to trash” choice should describe what it stops and await the actual conditions needed before any disk operation.
5. **Make permanent deletion observable.** Confirm the exact selection and irreversibility, revalidate it at execution, serialize conflicting operations, retain failures, and show progress and partial outcomes. Tests should cover active work, duplicate titles, custom roots, corrupted/missing files, concurrent writers, interrupted cleanup, and reinstall/disposal.
6. **One public npm bundle, distinct source modules.** Keep host, client, storage adapter, and domain code navigable without prematurely splitting them into separately published packages. Publish compiled output with explicit exports and a conservative `files` allowlist.
7. **Native presentation.** Adopt host locale, semantic tokens, existing menu/dialog controls, keyboard navigation, visible focus, reduced motion, and responsive layouts. Prefer documented slot contributions with stable session IDs over DOM/text heuristics.
8. **Mise baseline.** Pin project Node/pnpm versions aligned with the observed host (`24.18.1` and `11.7.0` as an initial compatibility baseline), use one project `mise.toml` for tools/environment/tasks, and ignore personal overrides. The exact versions are a project choice, not registry eligibility. Mise documents those sections and local precedence; the parent agent owns environment setup in this task. [Official mise configuration](https://github.com/jdx/mise/blob/main/docs/configuration.md); [installed runtime versions](/Users/jam/Documents/codespace/personal-projects/dsh-session-bin/.local/dsh-runtime/dsh/desktop-runtime.json#L3).
9. **Agent-ready docs.** Keep a short project instruction entry, a domain/architecture description with Archive/Trash/Purge distinctions, a current-host compatibility matrix, storage safety contract, development commands, and release/package checklist. Store detailed evidence here rather than repeating remote excerpts in every instruction file.
10. **GitHub conventions.** When a repository is eventually created, include license/attribution, contribution and security policies, bug/feature templates, a PR template with behavior/validation/compatibility, CI for checks and packed installation, screenshots, and release notes. Public publishing remains a later authorized action. GitHub's official Node publication tutorial confirms release-triggered CI publication and public scoped-package handling; credentials/trusted-publisher setup are not configured here. [GitHub package publication tutorial](https://github.com/github/docs/blob/main/content/actions/tutorials/publish-packages/publish-nodejs-packages.md).

## Open questions before implementation and release

- What public repository owner and npm scope/name should be used? `dsh-session-bin` is only a working candidate.
- Is the first release strictly for installed `0.2.0-rc.2`, or which additional tested DSH cohorts must be supported? Broad untested compatibility would recreate the reference's patch burden.
- Which documented slot exposes stable per-session sidebar action data on the supported host? If none exists, a first-class manager/settings/header surface is safer than guessed row identity.
- Should trash ownership be entirely plugin-local, or use native archive transitions with a tombstone ledger? This decision must preserve preexisting archives and restore intent.
- Can an upstream persistence deletion/quarantine capability be added later, or must a specific JSONL adapter be maintained? Its lease, shutdown, cache, attachment, parent/child-session, and crash-recovery semantics need implementation review.
- Should automatic retention-based purge exist? It should be opt-in and needs a concrete recoverability, scope, and activity policy; no such feature is assumed for the first release.
- Can the release claim a meaningful distinction from the already-listed reference? Catalog review explicitly evaluates overlap; acceptance is not automatic.
